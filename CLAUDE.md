# PONI GBP Manager

Automates Google Business Profile (GBP) review replies, location reports and local posts for PONI, a marketing agency. One developer (the owner) builds it with AI help.

This repository (`dotfournine/poni-gbp-manager-engine`) holds the engine, its tools, the knowledge base, the API contract and the deployment files. Two clients of the API are built outside this repository: the web app (the dashboard; its builder fetches `api/openapi.yaml` from `main`, and the old React-admin dashboard repository is no longer maintained) and the iOS app (`poni-gbp-manager-ios`).

`docs/` is the source of truth: `architecture.md` (the system, with the requirements FR-1 onward), `decisions.md` (the decisions in force, D-001 onward), `work-items.md` (what is left to build) and `runbook-google-mock.md`. Read the relevant part before designing anything. A change of direction is proposed to the owner first and then recorded as a new entry in `docs/decisions.md`; a superseded entry becomes a one-line pointer to the one that replaced it. A work item is removed from `work-items.md` when it ships. C++23 with Boost is settled (D-001, D-002).

## Commands

Engine, natively on macOS (from `engine/`; needs `export VCPKG_ROOT=~/vcpkg PATH="/opt/homebrew/bin:$PATH"`):

```bash
docker compose -f ../deploy/docker-compose.dev.yml up -d --wait db   # PostgreSQL on 127.0.0.1:55432
PONI_PUBLIC_FOLDER=/tmp/poni-public docker compose -f ../deploy/docker-compose.dev.yml --profile public up -d public   # the public folder on 127.0.0.1:8088 (D-105)
scripts/build-locked.sh cmake --preset macos-llvm
scripts/build-locked.sh cmake --build build/macos-llvm -j 4
scripts/build-locked.sh ctest --test-dir build/macos-llvm -j 4   # all tests; -L unit or -L integration for one group
./build/macos-llvm/poni-gbp-engine           # the daemon: http://127.0.0.1:8080/api/health
```

Every configure, build and run of the whole test suite goes through `engine/scripts/build-locked.sh`, never with more than `-j 4`: this Mac has 8 GB, and builds from two worktrees at once ran it out of memory. The script waits for its turn across every checkout and worktree and says who holds the lock. In a second worktree give the build a directory of its own (`-B build/macos-llvm-<name>` at configure, and use that directory in the next two commands), because the test database's name comes from the build directory's name. One test binary with a `--gtest_filter` needs no lock.

Tools and knowledge base (from `tools/`; needs `uv`):

```bash
uv run poni-tools migrate                    # apply pending migrations (--status: only show them)
uv run poni-tools check                      # the knowledge base: schemas, cross-checks, complete packs
uv run poni-tools seed                       # check, then replace the kb_* tables of the database
uv run ruff check . && uv run ruff format --check . && uv run pytest -q
```

Without `--config`, the engine and `poni-tools` read `~/.config/poni-gbp/engine.env` if it exists (README, "Local secrets"), so both work on the same database. `PONI_DEV_LOGIN_EMAIL` there switches on development sign-in, which the dashboard and the contract check use locally. Whether a GBP token is stored and Google accepts it is on the dashboard's status page, where the account is connected.

Engine in the Linux container, exactly what CI runs (from the repository root):

```bash
engine/scripts/linux.sh test
engine/scripts/linux.sh contract   # needs `npm ci` in api/
```

API:

```bash
cd api && npm ci && npm run lint && npm run check:contract      # needs a running engine with development sign-in and a public bucket or a folder for one (it builds a report); creates a test client
```

Every workflow by hand on made-up data, against the local mock of Google instead of the real one (D-087): `docs/runbook-google-mock.md`. The mock gets its own database and config file; never point it at the real ones.

```bash
uv run poni-tools mock-google                # from tools/: http://127.0.0.1:8090, the portal at /
```

`engine/scripts/linux.sh ai-live` runs the adversarial suite (the packs in `knowledge/`) against the real model with the knowledge base's defaults (needs `PONI_LLM_DASHSCOPE_BASE_URL` and `PONI_LLM_DASHSCOPE_API_KEY`; it costs a few cents). It is never part of the tests.

Before calling work done: the macOS tests and the Linux container build (`linux-clang`, the only Linux preset: GCC support was deleted, D-091 point 8) pass, the tools' checks pass, and for API changes the checks above pass. Warnings are errors (`PONI_WERROR`).

## Rules that protect clients

- **The engine deletes two things at Google: a local post, when a signed-in person asked for that post to be removed (D-088), and, in its own public bucket, the original of a report's page once it was copied to the archive (D-104).** **Never call any other GBP delete endpoint** (reviews, replies, locations, media, anything else). The API reports `canDelete: true` even for a manager account. The outbound client sends a DELETE only to `…/accounts/{a}/locations/{l}/localPosts/{p}`, without a body, and with ids that are plain (letters, digits, `-`, `_`), so that none can be `..` and walk the address up to the location; at Cloud Storage only of a report's page, `r/<token>.<ext>`, in the configured public bucket (`http::is_report_page_delete_url`), as the engine writes the address, and never without a configured bucket.
- **Secrets never enter the repository**: no tokens, keys or passwords in code, tests, fixtures, logs or docs. They live in `~/.config/poni-gbp/` locally and in the environment in production. Don't read those files into the project or print them.
- **Reviewer data stays out of git**: no raw API response or evaluation output with a reviewer's name is committed. Fixtures use sanitized data only.
- Review text is untrusted input everywhere, above all in LLM prompts (architecture section 10).
- **Nothing but `poni-tools seed` writes the `kb_*` tables** (D-078): no API route, no dashboard page, no migration, no job. The engine reads them on each use, in one statement where two tables must agree, and caches none of it: a new version is in effect with the next read, and nothing in the engine watches for one or notifies anyone (D-084). A change to what every client shares is a reviewed change to the files in `knowledge/`, published and seeded; prompts, the judge's rubric and the reply checks stay in code. The rule for copies (D-084, D-107): a location's content settings and reply settings are its own complete rows (`content_settings`, `reply_settings`), written from the knowledge base's defaults when the location is discovered (`repo::write_default_settings`, D-102, D-107) and never read from the knowledge base afterwards; a client has none. Nothing is merged when they are read: a row that cannot be read is an error the reader names (`repo::stored_settings`), and a field added later reaches stored rows by a migration, never from a default at run time. What nobody can change is read from the tables (the industry profile, the common flags, the corpus, prices). So the one reference is `locations.industry_key`, by key and without a foreign key; the API does not say whether the key is still in the knowledge base, the dashboard compares it with `GET /api/knowledge`; a location whose industry is gone is not analyzed. Every change to `knowledge/` gets a new `version` in `manifest.json` (`YYYYMMDD`, or `YYYYMMDD-N`).
- **A location's content and reply settings change in two ways and no other (D-107, D-102).** A signed-in person's `PUT` of a whole bundle with `If-Match` (`repo::replace_content_settings`, `repo::replace_reply_settings`, checked by `domain::check_content_settings` and `domain::check_reply_settings`), and the default rows written once when the location is discovered (`repo::write_default_settings`, called by `apply_discovery` in the transaction that inserts the location). Linking, unlinking and moving a location (`repo::update_location`, the one place that changes `locations.client_id`) leave them as they are: a client has no settings. No route copies settings between locations and no code saves them on its own, and the engine's one write, `auto_reply_enabled = false` when a location is switched off (`repo::update_location`), is the only other change. A save, the defaults at discovery and a migration start no go-live test: the one exception stays D-077's, noticed where a running test compares its fingerprint. A change to the reader keeps `ReplySettingsGolden.*` green; its fingerprints are recaptured only by a change that alters a reply prompt on purpose, named in the decision record (as the wording of the sign-off, the business's name and the language did once, D-107 points 9 to 11, all goldens in one recapture); its settings follow the domain types.
- **An industry is supported only with a complete pack**, which `poni-tools check` enforces: at least 2 corpus cases for every severity flag that applies, 10 manipulation cases (one Chinese, one mixed language) and 3 ordinary ones. A corpus carries no signature (D-082): a person reads new and changed severity and manipulation cases in the pull request, so say in the pull request which cases are new.
- **The engine changes a Google Business Profile in four ways and no other (D-061, D-088, D-099):** a PUT of a reply to a review (`gbp::ReplyWriter`, called only by `jobs/posting.cpp`), the create of a local post, the delete of a local post, and the update of a local post in the fields an approved edit names (`gbp::LocalPostWriter`, to be called only by the jobs `local_posts.publish`, `local_posts.remove` and `local_posts.edit`). The outbound client (`http/client.hpp`) holds each to its address: a PUT only to `…/reviews/{r}/reply`, a DELETE only to `…/localPosts/{p}` (and at Cloud Storage, below), a PATCH only to `…/localPosts/{p}?updateMask=<names>`, and a POST to `mybusiness.googleapis.com` only for `…/localPosts` (the create) and the read-only `batchGetReviews`. Any other PATCH, to any host, is refused. Each of these addresses is taken only as the engine itself writes it: plain ids, nothing percent-encoded, equal character for character to the address built from its parts, and no query, with one exception: the PATCH's query is exactly `updateMask=` and one or more of six field names (`summary`, `callToAction`, `event`, `offer`, `media`, `languageCode`), each at most once, joined by commas (`http::is_local_post_update_url`). The six are held twice on purpose, there (`http::kLocalPostUpdateFields`) and in `domain::kLocalPostEditFields`, so that widening the second does not widen the first, and a `static_assert` holds them equal. No request names a host with other characters than letters, digits, `.` and `-`, or carries a header that would change its method, host or length (`X-HTTP-Method-Override`, which Google honours on a POST, among them). The rule is one function, `http::why_refused`, asked before a name is resolved; `FakeHttp` asks it too, so a connector that builds another request fails its test. At Cloud Storage the client takes a POST only for an upload or for the copy of a report's page from `r/` to `a/` in the configured public bucket, and a DELETE only of an `r/` page there (`http::is_report_page_copy_url`, `http::is_report_page_delete_url`), each address equal to the one built from its parts, the `/` of the object's name as `%2F` and nothing else encoded, no query, and neither without a configured bucket. At Google's Admin SDK (`admin.googleapis.com`) the client takes one request, a GET of the list of the account's users, `…/admin/directory/v1/users?customer=my_customer&maxResults=500` with at most a page token after it, the address equal to the one the engine writes (`http::is_directory_user_list_url`); every other method and address on that host is refused, one user by id or by address among them, so the engine can change nothing in a Workspace and never asks about one person (D-106 point 3). A change to what may go there gets a line in `tests/unit/write_path_test.cpp` and keeps `OutboundDirectory.*` green. At Google Places (`places.googleapis.com`) the client takes one request, a GET of `…/v1/places/<id>` with a place id (`http::is_place_id`: 1 to 1,024 letters, digits, `-` and `_`, because Google documents no maximum length), no query, and the header `X-Goog-FieldMask` once and exactly `timeZone` (`http::is_place_time_zone_request`, D-109); every other request there is refused, and a change keeps `OutboundPlaces.*` green. The client does not limit a POST to any other host: that the engine sends no POST to another Google service than the ones it has (the OAuth token, Pub/Sub pull and acknowledge, the Gmail send) is a rule for the code that calls it. Don't widen an address, don't add a fifth write, don't add a second PATCH or a seventh field to the mask, and don't change a post's kind or the time Google publishes it at: for those a person still copies the post and removes it. A new refused shape gets a line in `tests/unit/write_path_test.cpp`, whose refusal tests run the real client in mock mode with nothing listening, so that a lost rule cannot reach Google from a test. With `PONI_GOOGLE_MOCK_URL` the client sends the same requests, checked on Google's address first, to the same path under the mock (`http://127.0.0.1:<port>/mybusiness.googleapis.com/v4/...`) and nothing else to any Google address but the mock's (D-087); the mock has no posts. The Performance API is read with GETs. The only other thing the engine writes at Google is an object in its own public Cloud Storage bucket (`connectors/storage`, a POST), and, under D-104, the copy of a report's page from `r/` to `a/` in that bucket and the delete of the original, the copy first; nothing else in a bucket is copied or deleted.
- **A reply is posted only after a signed-in person approved that exact text (D-062), or by auto reply where a person switched it on (D-069).** Exactly two functions enqueue `replies.post`: `repo::approve_draft` (a person) and `repo::schedule_auto_reply` (the policy, called by the pipeline for a draft routed to auto reply). Don't enqueue it from anywhere else, and don't add a third. Both end in the same job and the same `repo::claim_post`; a new condition for auto reply goes into `auto_verdict` in `repo_posting.cpp`, which runs when the draft is scheduled and again at the claim.
- **A local post reaches Google only after a signed-in person approved that exact content (D-088 point 3).** The approval carries the content the person read, and `repo::approve_local_post` refuses it unless it equals what is stored, field for field, after the same normalizing (`domain::normalize_local_post`). It is the only function that enqueues `local_posts.publish`; don't enqueue that job from anywhere else, and never publish a post by a schedule, a policy or a model. The claim (`repo::claim_local_post_send`) checks again that the content the post holds is the content that was approved (`approved_content`), reads both posting switches in its own transaction, and runs the checks again; a post it stops returns to `draft` with the reason and is never sent later by itself. Scheduling and repeating are Google's: the engine sends the post at once with its `scheduled_time`, and has no timer for posts. Only a draft can be rejected, and only a draft's own content is replaced by a person's save (`repo::edit_local_post`); a post that is at Google is changed there by an edit of its own, under the rule below (D-099). Only a `draft` or a `rejected` post is deleted from the database, by `repo::delete_local_post` (D-094); nothing that was ever sent is, `failed` included, because a send that was given up is still adopted when its post turns up at Google. A copy of a post (`repo::copy_local_post`) is a new draft that queues nothing and remembers the post it was copied from (`copied_from_id`, D-098), which changes nothing about either post; it brings no photo or video from a post made at Google, and the engine fetches nothing from Google's media hosts.
- **A create of a local post is sent once (D-088 point 6).** After the claim the job throws nothing until the bookkeeping is done. Only an answer that says for certain that nothing was created is a refusal: HTTP 400, 401, 403, 404 or 429, or no request at all for want of a token (`definitely_refused` in `jobs/local_posts.cpp`). A rate limit or a token error then returns the post to `approved` for the job's next attempt, anything else returns it to `draft` with Google's message. Every other answer leaves it open (a timeout, a dropped connection, a 5xx whatever its body says, a 408, 409 or 499, a 2xx whose answer can't be read): the post becomes `unknown` and the create is never sent again, by the job, by a retry or by a person (an `unknown` or `failed` post cannot be approved; it is copied as a new draft). The sync settles it, and gives a post at Google to the send that started last before the post was created, never to one that had been given up long before. An approval is carried out within 30 minutes or not at all (`approval_valid_for`): a job that runs late, after an outage or a restored backup, sends nothing. Don't add an answer to the list of certain refusals without Google's documentation for it. A new way for a send to happen, go wrong or be stopped gets a test in `integration/local_posts_publish_test.cpp`, and a change to sending keeps that file and `integration/local_posts_sync_test.cpp` green.
- **A post that is at Google is changed there only after a signed-in person approved that exact edit, by one PATCH per approval (D-099).** An edit is a row of `local_post_edits` beside the post, at most one per post (`draft`, `approved`, `sending`): the post keeps its row, its id, its `google_name` and its history, and its `content` stays what Google has until Google accepted the edit. Only a post that is `sent`, has a `google_name`, has no removal requested and belongs to a synced location has one, and only if its content is something a draft can hold: a post that holds what a draft cannot (an alert, a button outside the six, an event without its dates) is not edited here at all, because an edit could not say how to keep that part. An edit changes neither the post's kind, nor its `scheduled_time`, nor its repeat (a 400 that names the member). **An edit never writes a field its author did not change.** A PUT carries the content and `based_on`, the post's content as the person saw it; it is refused (`local_post_changed`) unless that is the post's content as the engine holds it now, and stored as the edit's base (`base_content`), on every PUT, also one of the same content. The fields the edit changes are those in which it differs from its base (`domain::local_post_edit_mask`, shown as `LocalPostEdit.fields`). Never take the base from the post's row without the client having said that this is what the person saw: a field that changed at Google meanwhile would become a change of theirs. The edit's content as the API serves it, and as an approval is compared with, is the post as it is now with those fields laid over it (`domain::local_post_with_edit`; `local_post_select` says the same in SQL), so a field the edit leaves alone always shows what the post has now. A post is its location's post with that id: the account in its stored name may be an old one. A list that could not be read marks nothing removed and gives up no send.
- **The sync of local posts never writes to Google and never sends a post again.** A send whose outcome is unknown is settled by reading: a post at Google that no row has yet, with the same content and created since the send, is adopted (`repo::store_local_posts`); without one the send is `failed` 15 minutes after it started, and staff are notified. Adoption runs before the list is stored, or the post would be taken for one made at Google. Against the Google mock nothing about posts is scheduled or started (D-088 point 13).

## API changes are spec-first

1. Change `api/openapi.yaml`; `npm run lint` in `api/`.
2. Implement in the engine. Response structs use Boost.Describe and must match the schema.
3. The web app's builder and the phone app read this file from `main`. Once the change is merged, tell both sides what changed in a message they can act on: the members renamed, added or removed, the new answers, and what the client must do.
4. `npm run check:contract` against the running engine.

**Responses stay compatible with the phone app (D-095 point 8).** From the app's first release, removing or renaming a member of a response, or narrowing an enum a response carries, is a breaking change: it is proposed to the owner and told to the app's side before it ships. Adding a member or an enum value is not, and the app ignores what it does not know. A request body is the other way round (D-092: a member the engine does not know is a 400), so the engine is released before the app version that sends a new request member. There is no API version route. `X-CSRF-Token` is an optional parameter in the spec because a bearer token needs none; a cookie session without it is still a 403.

Errors the engine produces have the shape `{"error": {"code", "message"}}` (`http::Response::error`). Internal details (SQL errors, host names) are logged, not sent. A repository function or service that may refuse a request returns `repo::Result<T>` (`db/failure.hpp`): it says `not_found("client")`, `invalid(message)`, `conflict(code, message)` or `unavailable(code, message)` where it checks the limit, and the handler answers with `respond(result)` (`http/api_support.hpp`), the one place a failure becomes a status (404, 400, 409, 502, 412, 428). Don't add a failure type or a mapper of your own. An edit of an existing thing goes through `api.change_if_match` (D-108): its single GET answers with an `ETag`, and a `PUT`, `PATCH` or `DELETE` without `If-Match` is a 428 and with a stale one a 412.

Something people must hear about is a notification: `repo::emit(tx, event, now)` in the transaction that caused it, with a key that is the same when the same thing is reported again. Review text goes in an event's body only, never in its subject. A new `system_problem` event is added to the list in the description of `NotificationEventType` in `api/openapi.yaml`, with its subject and the ids its push carries.

Every route is added with a `RouteInfo`: who may call it (`Access::user` unless it is part of signing in) and the action's name. The router asks the authorization hook before the handler runs. A handler gets the `Api` context (`http/api_support.hpp`): it reads with `api.query(f)` and changes data with `api.change(request, f)`, which runs `f(tx, audit)` through `audit::transact` in the signed-in person's name and refuses to commit a change that recorded no audit entry (a `repo::Result` that holds a failure is a refusal: it needs no entry, and nothing of it is committed); work the engine does on its own records with `audit::Actor::system("component")`. A GET of one thing by its id is one line, `add_get_by_id(...)`. Review changes seen by the sync go to `review_events`, not the audit log (D-039).

## Database

- Migrations are numbered SQL files, `engine/migrations/NNNN_lower_case_name.sql`, with no gaps. `poni-tools migrate` runs each once in its own transaction and records it with a checksum in `schema_migrations`; the engine applies none (`db::migrations_problem` only checks).
- The first is `0001_baseline.sql`, which replaced migrations 0001 to 0026 once, while nothing was deployed (D-091 point 10). `poni-tools migrate` marks a database that has exactly those 26 as having the baseline and refuses one that has only some of them; that code (`BEFORE_BASELINE` in `migrate.py`) goes once no such database is left.
- Never edit a migration that has been applied anywhere, the baseline included; add a new one. The engine refuses to start while migrations are pending or no knowledge base is seeded. A migration seeds no knowledge: that belongs in `knowledge/`.
- Blocking libpqxx calls run only through the `Database`: `co_await db.tx([](pqxx::work& tx) {...})` for one committed transaction (the callable may return nothing), `co_await db.audited(actor, now, [](pqxx::work& tx, audit::Writer& audit) {...})` for a change that needs an audit entry, and `db.run` only for what is not one committed transaction. Don't write a transaction wrapper of your own. The lambda runs on a pool thread: it must not touch state owned by the `io_context` thread.
- Pass time from the engine's `Clock` as a parameter (`db::to_timestamptz`); don't use SQL `now()` in queries whose behavior tests need to control.
- Raw API payloads are stored as `jsonb` next to the typed columns. A local post's content is one `jsonb` column, `content`, next to `approved_content` (D-091 point 13).
- SQL lives in the repositories (`db/repo_*.cpp`) as functions that take a transaction. libpqxx expands a container into separate parameters, so pass a list as one JSON parameter (`db::json_list`, `jsonb_array_elements_text`). Timestamps leave the database as text through `db::iso(column)`. Read rows into the API's structs by column name, not by position: `db::rows_as<T>`, `db::row_as<T>`, `db::one_as<T>` (exactly one row) and `db::page<T>` (`db/sql.hpp`; `repo_catalog.cpp` shows how), with `expr AS member` for anything that is not a plain column. A member the code fills in after the read is named at the call (`db::FilledLater{"review"}`, as in `repo_cases.cpp`), never given a made-up column or a mirror struct.

## Jobs

- Background work is a job in the `jobs` table: `queue.enqueue({.kind = "...", .payload = ..., .run_at = ..., .idempotency_key = ...})`. To enqueue atomically with a data change, use `jobs::sql::enqueue(tx, ...)` in the same transaction.
- Delivery is at-least-once. Handlers must be safe to run twice; give every job that must not be duplicated an idempotency key.
- A handler returns normally to succeed and throws to be retried (backoff 30 s doubling to 1 h, `max_attempts` default 5).
- Recurring work is registered with `Registry::every` in its job class's `install`, and the scheduler starts it; not a timer of its own.

## C++ conventions

- **Use only the C++23 subset that works on both libc++ 23 (macOS) and libstdc++ 15 (Linux; the Linux build is clang with libstdc++).** Not available on both: `std::generator`, `std::stacktrace`, `std::move_only_function`, `std::views::chunk`, `std::spanstream`, `std::mdspan`, `std::chrono` time zones (use cctz through `domain/posting_schedule.hpp`, D-110; it reads the operating system's zone files, so an image needs `tzdata`), `import std`. Fine on both: `std::expected`, `std::print`, `std::format`, `ranges::to`, `views::enumerate`/`zip`, `fold_left`, `flat_map`, deducing `this`. Apple's own clang can't build the engine.
- **Async**: one `io_context` thread runs all coroutines (`boost::asio::awaitable<T>`, `co_await ... use_awaitable`), so engine state needs no locks. Never block that thread: database work goes through `Database::run`, waits use Asio timers.
- **Coroutine pitfalls**: `co_await` isn't allowed in a `catch` block, so catch, store the error, and act after the block. Put a value in a named local before `co_return` or a `co_await` argument, and prefer member coroutines over coroutine lambdas inside a coroutine. Coroutine lambdas with captures must outlive the coroutine; take parameters by value in coroutines that outlive their caller.
- **Errors**: exceptions for infrastructure failures (database, network, bugs); `std::expected<T, E>` for outcomes the caller is expected to handle (validation, "not found", an API answering with an error). Don't use exceptions for control flow. Top-level loops (workers, scheduler, HTTP sessions) catch, log and carry on.
- **JSON**: map with Boost.JSON and Boost.Describe structs through `core::from_json` / `core::parse_json` (`core/json.hpp`), whose errors name the missing field. That reader is for what Google and the models send: it ignores unknown keys, and Google omits empty arrays, so every list field in a Google payload is `std::optional<std::vector<T>>`. A request body goes through `core/body.hpp` instead (D-092), where a member's type says what the schema says: `T` is required and never null, `std::optional<T>` may be left out, `core::Nullable<T>` may be left out or null (a PATCH member that can be cleared), `core::Partial<T>` is an object with some of `T`'s members, and a struct with `sent_whole = true` always travels whole. A member the struct does not have, a null where none is allowed and a missing member are a 400 that names the member; `100.0` is an integer.
- **Time**: take it from an injected `core::Clock`, never `system_clock::now()` directly, so tests can move time.
- **Outbound HTTPS**: go through `http::Client` (`NetClient` uses `core::make_tls_client_context()`; vcpkg's OpenSSL has no CA certificates, so the OS bundle is loaded explicitly). Take a slot from the `core::RateLimiter` before every call to an external API, and build URLs with Boost.URL segments so an id can't change the path.
- **A call to a Google API** goes through `google::send(api, limiter_key, request)` (`connectors/google/auth.hpp`; `google::fetch_json` when the answer is read, `google::url` for the address), and a connector takes a `google::Api`, except the Places time-zone read (`connectors/google/places`), which carries a key and no token (D-109). `google::send` gets the token, takes the limiter slot, sends again once after a first 401 and after nothing else, returns any other answer outside 2xx as an `ApiError` with Google's status (a token that could not be had is never returned as `not_found`, because callers read that as "it is gone"), and pauses the API after a 429. Don't write that loop in a connector, don't send anything twice from one, and don't catch a transport failure on the way: for the four writes a throw means "the outcome is unknown", and `definitely_refused` reads the status.
- **Google errors**: a connector returns `google::Result<T>`; an `ApiError` says what kind (not found, unauthenticated, rate limited). Transport failures throw. Recurring jobs record such errors for the status page (`integration_status`, `locations.last_sync_error`) and return; per-item jobs throw to be retried.
- **Logging**: `log::info("message", {{"key", value}})`. One event per line, JSON; put variable data in fields, not in the message. Never log secrets or review text at `info`.
- **Text**: there is no pattern library (D-058) and `std::regex` is not used; the reply checks are plain scans over code points after `text::fold` (full-width forms to ASCII, zero-width characters dropped). Nothing converts or checks Chinese script (D-056): the analyzer says which script a review is in, and the generator is told the script of the location's Chinese variant, or to match the review's when none is set (D-107 point 11). Lengths are counted in code points (`text::length`).
- **The LLM**: go through `llm::Client`. Providers are configured as `PONI_LLM_<NAME>_BASE_URL`, `_API_KEY` and `_PROTOCOL` (`openai` or `anthropic`, required), any number of them; every call names its provider, which is a setting per task (D-059). A call returns `llm::Result<T>`; `Error::configuration()` (wrong key or address) always fails the job, `Error::transient()` is retried and recorded on the last attempt (D-048). A request's temperature is optional: nothing is sent when the task's "send a temperature" setting is off, and never to a provider with the Anthropic protocol, whose API refuses one. The writer's temperature is `ReplySettings::temperature`, a field of a location's reply settings; the analyzer's is one global setting. Tests use `test::FakeLlm`, which also answers the judge. Never log a prompt, an answer or review text.
- **Compile time**: keep Beast socket and parser headers inside `http/server.cpp` and `http/client.cpp`; other files use `Router`, `Request`, `Response` and `http::Client`.
- Headers start with a short comment saying what the component is for. Comment the why, not the what.
- Dependencies come from the vcpkg manifest (`engine/vcpkg.json`, baseline pinned; the same commit is in `engine/Dockerfile`). Adding one is a decision: prefer Boost where it's the standard.

## Tests

- Unit tests (`tests/unit`) need no database. Integration tests (`tests/integration`) derive from `test::DbTest`, which gives each test its own database: a copy of the one `poni-tools test-db` migrated and seeded for this build (`poni_test_<build>` on the server of `PONI_TEST_DATABASE_URL`, default: the dev database's server). `ctest` prepares it first, as a fixture, from `knowledge/`; with a problem in the knowledge base it stops there and says why. To run a test binary by hand, prepare it once (`uv run poni-tools test-db --name <name>`). Tests fail, not skip, when there's no database.
- A test that needs "a new version of the knowledge base" changes the `kb_*` tables of its own copy with `reseed(sql)` (`engine_fixture.hpp`); that the real seed replaces the tables is tested in `tools/tests`. `become_test_client(client, industry)` gives each location linked to a client its pack's industry, switches it on in the test's own database and saves both of the made-up business's complete bundles, its content and its reply settings, through the repository. `set_content` and `set_reply` (`engine_fixture.hpp`) lay a few members on a location's stored bundle, unchecked and without a person's save, and `save_content_settings` and `save_reply_settings` (`api_fixture.hpp`) do the same through the `PUT` with `If-Match`.
- Use `core::ManualClock` and `Worker::run_once()` / `Scheduler::tick()` to test time-dependent behavior without sleeping.
- Connectors sit behind interfaces so tests use fakes (`tests/fakes.hpp`: `FakeHttp`, `FakeGbp`, `FakeSubscriber`, `FakeIdentityProvider`, `FakeLlm`, `FakeChannel`); tests never call Google or an LLM and never send email. `FakeGbp` takes replies and holds them back until `publish_held()`, as Google does; `FakeLocalPosts` keeps a new post in processing until `finish_processing()`.
- `test::ReplyTest` (`integration/reply_fixture.hpp`) adds two locations, a staff member, the pipeline, the poster and the notifier to `EngineTest`. A change to posting must keep `integration/posting_test.cpp`, `integration/auto_reply_test.cpp` and `integration/go_live_test.cpp` green, and a new way for a post to happen, go wrong or be stopped gets a test there. The fixture fixes the point in the delay range (`roll_`), so a test knows when an auto reply is due.
- `test::EngineTest` adds a `ManualClock` and the job queue to `DbTest`; `test::ApiTest` adds the router with sign-in, `sign_in()` returns a browser with a session, and `app_sign_in()` returns the phone app's token, which a call sends with `bearer(token)`. Every sign-in in a test comes from one address, and the attempt limit counts 20 in 10 minutes: a sign-in is two attempts (start and callback), for the app as for the dashboard, and the app's exchange counts on a limit of its own.

## Clients of the API

- The web app (the dashboard) and the phone app are built outside this repository, from `api/openapi.yaml`. What the engine relies on from them: the dashboard always sends `X-CSRF-Token` with a changing request; an approval sends the content exactly as the client got it from the engine; a photo or video is sent as the file the person picked. Review text, a post's text and what a model wrote are rendered as plain text by both.
