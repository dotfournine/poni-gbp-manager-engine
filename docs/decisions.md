# Decisions

The decisions in force, by number. Code comments and `CLAUDE.md` cite these numbers, some with a point ("D-088 point 6"), so numbers and point numbers are never reused; a point missing from a numbered list was superseded. Each entry says what holds today, with any later amendment already applied. `CLAUDE.md` has the operational rules in full.

A change of direction is proposed to the owner first and recorded as a new entry with the next number. The entry it replaces becomes a one-line "Superseded by D-xxx" pointer.

## Stack and build

### D-001 · The engine is written in C++23
The owner and AI maintain it; C++26 compiler support is still partial.

### D-002 · Networking uses Boost.Asio and Boost.Beast
Coroutines keep async code readable.

### D-003 · The engine owns every external integration
The dashboard and the phone app talk only to the engine: one place for credentials, rate limits and audit.

### D-004 · The API is REST/JSON, spec-first in OpenAPI 3.1
`api/openapi.yaml` is the one contract; clients are generated from it.

### D-005 · PostgreSQL is the system of record and the job queue
One datastore to run; `SKIP LOCKED` queues are enough at this scale.

### D-011 · The dashboard is React-admin, TypeScript and Vite, a static SPA
Use React-admin's and Material UI's components; no hand-built components, no other UI library.

### D-014 · libpqxx on a dedicated thread pool
There is no maintained Boost-native PostgreSQL client. Blocking calls go through `Database`, never on the `io_context` thread.

### D-028 · Toolchain
Homebrew LLVM on macOS; Ubuntu 26.04 with apt.llvm.org clang in containers (`linux-clang`, the only Linux preset, built against libstdc++); vcpkg manifest with a pinned baseline and overlay triplets. Engine code uses only C++23 that works in both libc++ and libstdc++ (`CLAUDE.md` lists what is not available). GCC is not supported (D-091 point 8).

### D-029 · Time zones come from a library, not `std::chrono`
libc++ has no `std::chrono` time zones. The library is cctz (D-110 point 2).

### D-034 · The engine builds for arm64 and x86_64 Linux
CI builds and tests both (D-091 point 9).

### D-079 · The engine is a daemon and nothing else
`poni-gbp-engine` takes no command. (1) Operations are `poni-tools` in `tools/` (`migrate`, `check`, `seed`, `pack`, `publish`, `test-db`); in Compose, `migrate` and `seed` run as one-shot services before the engine, which at start only checks: no pending migration, a seeded knowledge base, the Google target (D-087). (2) The GBP managing account (D-043), the sending mailbox (D-066) and the Workspace administrator (D-106 point 2) are connected by a signed-in person from the dashboard (`http/connect.hpp`). The account's checks run, and the token is stored encrypted with an audit entry in that person's name; secret, token and key never reach the browser or a log. (3) Tests start from a copy of one database `poni-tools test-db` prepared per build; the engine applies no migration.
Why: one process with one job is easier to reason about, and no second codebase handles the client secret and the encryption.

### D-091 · The engine simplified
(1) Pub/Sub stays beside polling. (2) A report's JSON is kept in `reports.data` only. (3) API surface no client used was removed. (5) The voice field `other_business_names` is removed: nothing read it. (6) Every setting stays. (7) No column is dropped only because nothing reads it. (8) GCC support is deleted. (9) CI builds both architectures. (10) Migrations start from `0001_baseline.sql`, which replaced 26 earlier ones once, while nothing was deployed; `ReplySettingsGolden` proves a code change alters no prompt; its fingerprints are recaptured only by a change that alters a reply prompt on purpose, named in the decision record, and its settings follow the domain types. An applied migration is never edited. (12) The sign-in ID token's signature is not verified: it is the token endpoint's answer to the engine's own code exchange over verified TLS (OpenID Connect Core 3.1.3.7). Its claims come only from `google::exchange_code` and are still checked; no other token is read without a signature check. (13) A local post's content is one `jsonb` column beside `approved_content`. (15) D-077 is accepted as built.

### D-092 · A request body is read exactly as the spec says
One parser (`core/body.hpp`): an unlisted member is a 400 naming it; `null` only where allowed; PATCH is JSON Merge Patch (RFC 7396); `100.0` is an integer; no route has its own rule.
Why: a body silently cut down makes a person believe a setting was saved. So the engine ships before a client that sends a new request member.

### D-108 · Every change of an existing thing carries its ETag
The owner's decision of 2026-11-25. (1) The single `GET` of a thing a person edits answers with an `ETag`, and so does a change of it that returns the thing. A `PUT`, `PATCH` or `DELETE` of it needs `If-Match` with that tag: without the header it is a 428 `precondition_required`, and with any other value a 412 `precondition_failed` that changes nothing. `If-Match: *`, a list of tags and a weak tag are a 412: a change is made only against the one thing its author read. A list carries no `ETag`, so a client edits from the single `GET`; a create and a `POST` action need none, and there is no `If-None-Match` and no 304. (2) The tag is a strong validator, `core::etag`: the quoted hex SHA-256 of one JSON object that holds the members the route's body can set, with the values the thing holds, built in one fixed member order (`repo::editable` beside the repository that reads the thing). What the engine writes by itself is never in it (times, counts, sync state, pause state, `last_run_on`), so a sync or a count does not make a person's view stale. A client's tag holds only what the client's `PATCH` sets (`name`, `notes`, `archived`): a location linked to it through the location's own `PATCH` does not make the client's view stale, and a client's `DELETE` unlinks the locations it groups when it runs, each unlinking audited and the `client.delete` entry keeping their ids. There is no version column: the tag is worked out from the row each time, and two rows that say the same have the same tag. (3) The check sits in the transaction that writes, after the row lock (`Api::change_if_match`): `current(tx)` locks the row `FOR UPDATE` and gives its tag, then `If-Match` is compared, and only then does the change run. Of two people who read the same tag, one waits on the lock and then meets a new tag. The checks come in this order: session and CSRF (the router), the body's shape (400: a member the schema does not list, a wrong type, a `null` where none is allowed), the thing (404), the header (428), the tag (412), then the change itself, which checks the body's limits (a length, a range). A stale save that equals what is stored is a 412; an up-to-date one is a 200 that records nothing and answers with the same tag. There is no `RouteInfo` member and no check in the router, because the router has no database. (4) Exempt, because something else already holds them to what the person read: an approval that carries the content approved (a draft's, a local post's, a local post edit's), status actions and their 409s, the `based_on` of a local post's edit (which the engine needs to work out the fields the edit changes, so `If-Match` is not added there too), a device's unregister, and the discard of a post's edit. (5) Caddy's `encode zstd gzip` (`deploy/Caddyfile`; seen with Caddy v2.11.9) answers a response it compresses with the encoding inside the tag's quotes, `"<hex>-gzip"` or `"<hex>-zstd"`, leaves the tag as it is on a response it does not compress, and passes `If-Match` on to the engine unchanged. `api_support::if_match_accepts` therefore takes those two forms of the stored tag as the tag, and nothing else. (6) The routes covered: `PATCH` and `DELETE /api/clients/{id}`; `PATCH /api/locations/{id}`, whose tag holds what that `PATCH` sets (`client_id`, `enabled`, `industry_key`, `analyze_from`, `audience`, `posting_enabled`), so that a discovery, a review poll and a pause do not make it stale; `PATCH /api/ai/settings`, without `providers`, `prompt_version` and `updated_at`; `PATCH /api/system/settings`, whose tag holds the two switches and none of the engine's pause columns or `google_target`; `PATCH` and `DELETE /api/notification-rules/{id}` (`recipients`, `enabled`); `PATCH /api/drafts/{id}` (`text`), whose check takes the review's lock and then the draft's, as every path that decides about a post does; and `PUT` and `DELETE /api/local-posts/{id}` (the post's content). Each `current` takes the lock its repository function takes first, so that it adds no lock order of its own. A thing whose status moved on since it was read still answers its 409 once its tag matches. A location's reply settings, its auto reply and the report schedules get the header where they are reshaped, in the order that reshapes them, so that no route gets it twice.
Why: a stale view must never overwrite a newer decision, least of all a safety switch.

## Data, sync and jobs

### D-012 · Pub/Sub over REST, not `google-cloud-cpp`
Pull and acknowledge only; no gRPC, Protobuf or Abseil for two HTTP calls.

### D-037 · Review sync: three paths into one idempotent store
(1) Every minute one `batchGetReviews` per account for the locations whose poll is due. (2) A full reconciliation per location on linking, then hourly. (3) Pub/Sub notifications. A review is marked removed only when Google answers `NOT_FOUND` for it.
Why: notifications lag about 15 minutes, a reply added elsewhere does not move `updateTime`, and Google's lists are not reliably complete.

### D-112 · How often reviews are polled is an engine setting
One interval for every location, `PONI_REVIEW_POLL_INTERVAL_S` (default 120 seconds, at least 60): a location is polled again that long after its last poll, or after its last failed poll. Due polls are picked up at the poll tick (`PONI_REVIEW_POLL_TICK_S`), which stays a setting of its own, so that a newly switched-on location is polled at the next tick and the locations do not all fall due at once. `locations.review_poll_interval_s` and its member of `Location` and of the location's `PATCH` are removed; `locations.next_review_poll_at` stays, as the engine's own state.
Why: how often reviews are read is the engine's scheduling, not an attribute of a location that staff edit.

### D-038 · Superseded by D-102

### D-103 · An audit entry names its location
The owner's decision of 2026-11-22. `audit_log.location_id` names the location an entry is about, or none, and the API serves it with the location's current title and filters by it (`GET /api/audit-log?location_id=`). It is recorded when the entry is written, never derived when the log is read: a draft or rejected local post, a schedule and a notification rule are deleted later, and their entries keep their location. `audit::record` reads it from the object in the statement that inserts the entry, so no caller can forget it; a caller names it only where the object is already gone (the three deletes). Which kinds of object have a location is listed in `AuditEntry.location_id`; a check on `audit_log` holds that those always name one. Entries written before are not filled in, because nothing changes an audit entry (the trigger of `0001_baseline.sql`), and nothing was deployed.
Why: after D-102 everything the engine does is a location's, and staff read the log of one store.

### D-039 · What the sync notices goes to `review_events`
Not to the audit log, which holds what people do and what the engine does to its own objects. Mirroring reviews would bury the audit log.

### D-044 · A review's language is first guessed from its script
Reviews carry no language field. The analyzer's answer replaces the guess and tells Simplified from Traditional.

### D-046 · Which reviews need work is read from the data
A review needs work when its current version has no analysis, or it has no reply and no live draft; a job every minute queues `reviews.analyze` for them, a batch at a time. A review with a reply gets an analysis, no draft.
Why: the pipeline is idempotent and self-healing; an edited review or a dead job is picked up by the next pass.

### D-055 · Superseded by D-102

### D-102 · A location is the unit of work; a client is bookkeeping
The owner's decision of 2026-11-22. Google's Business Profile has accounts and locations and no clients, so everything the engine does is a location's, and a client only groups locations. (1) A client is a name, notes, an archived flag and its locations, and nothing else: no setting, switch, go-live test, report, schedule, notification rule or model cost hangs on it, and no workflow reads it. Linking, unlinking, moving a location to another client and archiving a client change only the grouping (audited); they change no setting, switch, test or report of the location. A person may delete a client, which unlinks its locations and changes nothing else about them. (2) Every location starts with everything off: `locations.enabled`, false at discovery. While it is off, the location is only listed: no review poll or full sync, no analysis or draft, no reading or sending of local posts, no help with posts, no go-live test, no report, no auto reply. Only a signed-in person switches it, through `PATCH /api/locations/{id}` (`enabled`), audited, and it needs no client; code and tests against a real database never switch it on. Switching it on needs an accessible location and starts a full sync (D-037 point 2); it switches nothing else on and lifts no pause. Switching it off switches the location's auto reply off (`reply_settings.auto_reply_enabled`, D-110), and the claims of an approved reply, a local post and an edit stop at it as at a posting switch (D-063); a requested removal of a local post still goes ahead, because deleting is the only way to stop a scheduled post. (3) A location's industry (`industry_key`), the day its analysis starts from (`analyze_from`: only reviews written on or after it are analyzed and drafted for, none means all; staff can still analyze an older one by hand) are the location's own, set by a person; who its customers are (`audience`), which the help with posts is told, is one of its content settings (D-107). The engine does not take an industry from Google's primary category; the dashboard may suggest one. A location whose industry is not in the knowledge base is not analyzed. (4) A location's content settings row and reply settings row are written from the knowledge base's defaults when the location is discovered, so every location has both, enabled or not (D-107). Nothing copies settings between locations; "like our other branch" is the dashboard filling the form from that location's settings. (5) A go-live test is started for one location (`POST /api/locations/{id}/go-live-test`). It tests that location's configuration at its policy's width, and its real reviews (D-075) are that location's. A pass counts for the fingerprint as before (D-074 point 2); one test per fingerprint runs at a time. (6) A report is one location's: `reports` and `report_schedules` name a location, a report covers that location alone, and its recipients are the `location_report` rules that name that location, so each store's manager can get their own store's report. The event type `client_report` is renamed `location_report`, and a "client report" is a location's report wherever the code, the API and the docs name one. (7) A notification rule names a location or none (every location). Model cost is summed per location (D-057). (8) The API reads by location: routes that filter by `client_id` (reviews, reports, local posts, escalations) filter by `location_id` instead, and a client's figures are read location by location, which is cheap because a client has a few locations at most. `GET /api/locations?client_id=` stays, because it is the grouping. A response may still name the client a location is grouped under, for display; reports, schedules, go-live runs, rules and model costs name a location instead. (9) Nothing that runs today stops: the migration enables every location linked to a client that is not archived and gives it its client's three fields. That carry-over is the one time anything but a person switches a location on. (10) The prompts name the business by the location's title, never by the client's name; `reply_name` is gone, so the title always names it (D-107 point 5).
Why: linking did two things at once, grouping and "we manage this one", and the second hid behind the first. Every setting, the fingerprint and the posts were already a location's. Per-location reports fit stores whose managers differ, and a client of a few locations costs nothing to read location by location. Supersedes D-038 and D-055.

## Google writes and posting safety

### D-042 · The outbound client is narrow by construction
PUT for one address (D-061), DELETE for one (D-088 point 4), PATCH for one (a local post with the fields an edit changes, D-099 point 4), a POST to `mybusiness.googleapis.com` only for `batchGetReviews` and the create of a local post; at `admin.googleapis.com`, a GET of the list of users and nothing else (D-106 point 3); and at `places.googleapis.com` one GET of a place's time zone (D-109). One function, `http::why_refused`, decides before a name is resolved, and `FakeHttp` asks it too.
Why: "the engine writes only these things to Google" is a property of the code, not a habit.

### D-109 · A location's time zone comes from Google Places
The owner's decision of 2026-11-25, in place of the Time Zone API by coordinates: a location's coordinates are user-provided and often missing at Google, while its place id is there for any location on Maps. (1) The engine reads a location's time zone once, when the location is newly discovered: one GET of `https://places.googleapis.com/v1/places/<place id>` (Place Details, Places API (New)) with the field mask `timeZone` in `X-Goog-FieldMask` and the key in `X-Goog-Api-Key`, and keeps `timeZone.id`, the IANA name. (2) The outbound client takes at `places.googleapis.com` exactly that request: a GET, the address equal to the one built from its parts with a plain id, no query, nothing encoded and no port, and the field mask present once and exactly `timeZone` (`http::is_place_time_zone_request`); every other method, path, query or field mask there is refused. Against the mock the same request goes to the mock (D-087). It is the one call to Google that does not go through `google::send` (`connectors/google/places`), because it carries a key and no OAuth token; it takes its own limiter slot (`google.places`). (3) The key is `PONI_GOOGLE_PLACES_API_KEY`, a Google Maps Platform key restricted to the Places API (New) and to the server's address. The engine refuses to start without it while a GBP OAuth client is configured and the mock is off; against the mock an empty key is sent as a fixed stand-in. It is never in a log line, an error message, an audit entry or an address: an error names Google's HTTP status and its `error.status` word, never Google's message.
Why: one read per new location gives the zone a place is in, as Google itself has it, without asking staff and without a coordinate the profile may lack. The field `timeZone` is billed as Place Details Pro, a few calls a month at most.

### D-061 · Replies are written by one PUT
`…/reviews/{r}/reply`, behind `gbp::ReplyWriter` (one method), called only by `jobs/posting.cpp`. The engine's writes at Google are exactly four: this PUT, the create and delete of a local post, and the edit of one (D-099). A wrong id cannot turn the call into an update of anything else.

### D-062 · How a reply is posted
(1) A post starts from a signed-in person's approval of the exact stored text, or from the policy (D-069). (2) The job reads the review from Google again; `repo::claim_post` checks in one transaction that it is unchanged with no reply but the engine's own, reads both switches, and opens a row in `reply_posts` (one open post per review). (3) One PUT. A 4xx means nothing was posted; a timeout, dropped connection or 5xx leaves the post open and is never retried. (4) `posted` on 200, `published` when a read shows it. (5) While a post is open nothing else is posted to that review; after `PONI_POST_CONFIRM_WINDOW_S` an unseen post is closed as unconfirmed and a person decides.
Why: Google shows a reply minutes after accepting it, and a second PUT replaces whatever is there.

### D-063 · Two kill switches
`system_settings.posting_enabled` (off after installation) and `locations.posting_enabled`. Both must be on to approve and are read again at the claim. A draft a switch stopped returns to the queue; switching back on posts nothing. They cover auto replies and local posts. Only people flip them.

### D-110 · Auto reply
The owner's decision of 2026-11-25. (1) "Auto reply" is a reply the engine posts without a person approving it, and everything that belongs to such replies carries that name: the route value `auto_reply` (stored in `reply_drafts.route`, served as `DraftRoute`, expected by a corpus case's `expect.action`), the columns `locations.auto_reply_*`, `system_settings.auto_reply_*` and `go_live_runs.auto_reply_*` (`0013_auto_reply_names.sql`, which renames the stored route value with them), the audit actions, the notification subjects and keys, the dashboard's link `/#/auto-reply`, the API's tag `auto-reply`, and the files and functions of the engine. Posting, `posting_enabled`, `replies.post`, `claim_post` and `reply_posts` keep their names: posting is the act of sending, for both kinds of reply. Local posts are never auto anything. (2) Auto reply's settings are flat members of a location's reply settings (D-107), stored as columns of `reply_settings` with the same names, and the per-location columns they replace are gone: `auto_reply_enabled` (the person's switch, default false), `auto_reply_min_stars` (4 or 5, default 5), `auto_reply_delay_min_minutes` and `auto_reply_delay_max_minutes` (0 to 1440, default 0 and 0), `auto_reply_window_start` and `auto_reply_window_end` (`HH:MM`, empty for none), `auto_reply_daily_cap` (1 to 1000, default 100) and `auto_reply_pause_after_failures` (1 to 20, default 3). The time of an auto reply is now plus a random delay between the two, moved into the window (its next opening plus the delay again); a window may cross midnight and is read in the location's IANA time zone through cctz, which reads the operating system's zone files, so an image needs `tzdata`. A window without a time zone the server knows, or a timing that cannot be used, means no auto reply, and a job that runs late outside the window does not post. A save that has `auto_reply_enabled` true is refused unless the location is switched on and accessible (D-102), the minimum is 4 or 5, the timing can be used, and a window has a zone the server knows; a save that moves the switch is also audited as `location.auto_reply_enabled` or `location.auto_reply_disabled`. Only a person's save switches it on; switching the location off switches it off (D-102 point 2, D-107 point 8). Code, migrations and tests against a real database never switch it on. (3) Auto reply is for reviews with text, and of at least `auto_reply_min_stars`. A review without text gets its draft from the same writer and goes to the approval queue with the reason `auto reply is for reviews with text`; there is no setting for it. The gate routes it so, and `auto_verdict` checks the review's text again at scheduling and at the claim (`Auto reply is for reviews with text.`), as it checks the stars: `domain::stars_may_auto_reply` keeps an explicit 4 beside the minimum, so three stars or fewer never auto reply whatever is stored. There are no per-star switches and no positive or rating-only flags. Dropping the per-star switches means `auto_reply_enabled` alone covers whatever `auto_reply_min_stars` says: the default of 5 and the go-live width check (a pass must cover the policy's width, D-074 point 2) are what keep four-star auto replies a deliberate, tested step. (4) What the engine keeps about auto reply is its state, not a setting: a location's and the global pause (`paused`, its reason, detail and time, `resumed_at`, on `locations` and `system_settings`), what was posted in the last 24 hours, what is scheduled, whether the timing can be used, and the go-live state. It is served only by `GET /api/system/auto-reply` (`AutoReplyStatus`, with an `AutoReplyLocation` for every switched-on location), never in the reply settings and never in their `ETag`, so a pause never makes a settings form stale. (5) The routes: `PATCH /api/locations/{id}/auto-posting`, `GET /api/auto-posting`, `POST /api/auto-posting/resume`, `POST /api/locations/{id}/auto-posting/resume` and `GET /api/auto-posts` are removed. `GET /api/system/auto-reply` shows the state; `POST /api/system/auto-reply/resume` lifts the global pause and nothing else; `POST /api/locations/{id}/auto-reply/resume` lifts that location's pause and nothing else; `GET /api/auto-replies` lists the replies posted without a person. None of these takes `If-Match`. `POST /api/drafts/{id}/unschedule` stays, under the tag `auto-reply`. There is no per-location auto-reply route: the settings are saved with the reply settings.

### D-069 · Auto reply
A draft routed `auto_reply` is scheduled by `repo::schedule_auto_reply`; it and `repo::approve_draft` are the only two that enqueue `replies.post`, and both end in `repo::claim_post`. The conditions, in `auto_verdict`, run at scheduling and again at the claim: the switches (D-063, `auto_reply_enabled`, D-110 point 2), the stars and a review with text (D-110 point 3), no pause and the cap (D-072), a go-live pass (D-074), route `auto_reply`, the pipeline's own words (D-067), an unedited review with no earlier draft or attempt, no open escalation, checks passing, inside the window (D-110 point 2). It reads the reply settings after it has locked the location's row, the lock a save and a switch-off take too. A draft that fails one later goes to the approval queue and is never scheduled again by code. A post is stood behind by a person or by the policy (`policy_version`), never both and never neither.
Why: one job and one claim mean every guard of D-062 holds for auto replies too.

### D-072 · Daily cap and pauses
(1) At most `auto_reply_daily_cap` automatic replies per location in 24 hours (a reply setting, default 100, D-110 point 2); at scheduling the scheduled drafts count too, at the claim only the posts. (2) The engine pauses a location after N drafts in a row failed a check (`auto_reply_pause_after_failures`, a reply setting, default 3), on an unconfirmed automatic reply, or when Google refuses one for good; everything, when the refusal concerns the shared credentials. Only a person lifts a pause (`POST /api/locations/{id}/auto-reply/resume` for a location's, `POST /api/system/auto-reply/resume` for the global one, each lifting its own only), and resuming posts nothing that was stopped. A pause is the engine's state, not a setting (D-110 point 4).

### D-076 · Amendments to auto reply
No earlier human-approved reply is needed before switching `auto_reply_enabled` on (the go-live gate is the safeguard); `auto_reply_daily_cap` defaults to 100; the pause counts failures in a row, per location, up to `auto_reply_pause_after_failures`. D-072 and D-110 are written with these applied.

## AI replies and go-live

### D-006 · Tiered reply policy with escalation
Every review ends as `auto_reply`, `approval_queue` or `escalate` (FR-5, FR-6). An auto reply to a serious complaint is the biggest business risk.

### D-010 · One LLM client, DashScope first
`llm::Client` is the one way to a model, with two protocols (D-074 point 8). DashScope (Qwen) through its US-region endpoint is the first provider; a key works only with its own region's address. The model is chosen per task.

### D-021 · Layered defences against manipulative reviews
Structured prompts, mechanical checks and the policy gate, with a permanent adversarial suite (`ctest -L ai`). Strangers write reviews; replies are public under the client's name. The layers today: D-058.

### D-022 · Localization per location
A location's own (D-107): the reply languages (English, Chinese, Spanish) and the fallback language are reply settings, and the Chinese variant (`zh-CN`, `zh-HK`, `zh-TW`) and the English variant (`en-US`, `en-CA`), each of which may be left unset, are content settings. The script is not verified by code (D-056).

### D-024 · Reply quality is rated by an AI judge from another model family
A judge of the writer's own family favours its writing. The rubric is in `domain/prompts.cpp`; the judge is D-031.

### D-030 · Default models
`qwen3.7-plus` for every DashScope task in `knowledge/defaults.json`; `qwen3.8-flash` is priced as the cost fallback. The model is a setting per task.

### D-031 · Claude Opus 5.5 is the judge
`claude-opus-5-5` through the `anthropic` provider by default; a different family from the writers.

### D-048 · How model failures are handled
A wrong address or key (`Error::configuration()`) fails the job and marks no review. A transient failure is retried and, on the last attempt, stored as a failed analysis or an empty draft for the approval queue (not escalated). A content-filter refusal is stored as failed at once. Every request is a row in `llm_calls` with an estimated cost.

### D-051 · Prompts are in code and versioned
Every analysis and draft records `prompt_version()` (a revision plus a hash of the prompt texts), the model and the inputs.

### D-056 · No conversion or check of Chinese script
The writer is told the script and phrasing; its text is stored as written. The analyzer says a review's script; without one the reply is Simplified.

### D-057 · Model cost is summed per location
And per model, provider, task and day; not per client (D-102).

### D-058 · Severity and manipulation are detected by the model alone
No keyword rules or pattern library. Code checks a reply only for links, email addresses, phone numbers, emoji, length and language (plain scans after `text::fold`). The offline suite proves a raised flag is always acted on and contact details are stopped even when both models were fooled; the live suite (`engine/scripts/linux.sh ai-live`, by hand) measures how often the model is fooled, and a prompt or check change needs a live run with no case reaching auto reply. Offers, promises and spelled-out contact details are not caught.

### D-059 · Several model providers
A provider is `PONI_LLM_<NAME>_BASE_URL`, `_API_KEY` and `_PROTOCOL` (`openai` or `anthropic`, required), any name. Each task names its provider and model; every call records its provider.

### D-064 · A draft with a failed check cannot be approved
Checks run on every edit and at approval, with no override: change the text, or the setting the check reads.

### D-067 · Regenerate with instructions
The staff member's words follow the rules in the writer's system message, and a rule wins a conflict. Such a draft goes to the approval queue (`regenerated_with_instructions`) and never auto replies: the adversarial suite never ran with added instructions.

### D-068 · "No reply needed"
A signed-in person can mark a review with no reply and none on its way: its draft is cancelled (kept), none is written, and it leaves the queue. Audited, undoable, optional reason; it ends when the reviewer edits the review. An escalation is untouched.

### D-074 · The go-live test gates auto reply
(1) A location's fingerprint (`domain::fingerprint`) hashes what changes what the models are asked and what code checks: rendered prompts, each task's provider, model, temperature, token limit and extras, the check limits, and `kGateVersion` (raised by hand when the gate or checks change). (2) A location auto replies only while its fingerprint has a pass covering its policy's width (`auto_verdict`). The width is `auto_reply_min_stars` alone (D-110 point 3): a pass at 4 covers 5, a pass at 5 does not cover 4, and a run records the minimum its cases were routed with (`go_live_runs.auto_reply_min_stars`). A pass switches nothing on. (3) A new fingerprint or a lower `auto_reply_min_stars` needs a new test; the switch, the cap, the pause after failures, the timing and corpus additions do not. (4) Until a pass, the location does not auto reply. (5) Only a signed-in person starts a run (`repo::start_go_live`), never code or a test against a real database. One job per case, with the real settings and the pipeline's prompts: the industry's corpus and the location's own reviews (D-075), 3 times each; replies routed to auto reply are judged. It fails when an attack or severity case reaches auto reply or a reply is "unacceptable"; only "passed" opens the gate. (6) The fingerprint sits beside D-069's policy version. (7) The writer's temperature is `Voice::temperature`; each task has a "send a temperature" switch. (8) `llm::Client` also speaks Anthropic's Messages API (`_PROTOCOL=anthropic`); the judge is its own task. (9) Nothing in CI calls a model.

### D-075 · A go-live test includes the location's own reviews
Up to 20 recent 4–5-star reviews of the location under test (D-102) with text, and none without: a review without text never auto replies (D-110 point 3), so it tests nothing. They go through `domain/prompts.hpp` (never the reviewer's name or photo); so real review text reaches the judge's provider during a test, and only then. Replies are kept with the run in the database only.

### D-077 · Details of the go-live test
(1) The newest pass or fail of a configuration decides. (2) A failed test runs to its end. (3) A setting changed under a running test cancels it and the engine starts a new test of the new configuration in the submitter's name: the one case in which the engine starts a test. (5) Only "unacceptable" fails. (8) The Anthropic protocol is never sent a temperature. (14) A provider's address and protocol are not in the fingerprint. (15) `PONI_LLM_<NAME>_PROTOCOL` is required.

### D-066 · Notifications
`repo::emit` raises an event in the transaction that caused it: one row per recipient in `notification_deliveries`, sent by a job, unique per recipient by its key. ### D-097 · Push notifications to the phone app
(1) `push` is a second notification channel beside email; channels stay plug-ins (`connectors/notify`). (2) The engine sends to Apple's push service (APNs) itself, over HTTP/2: nghttp2 (a vcpkg dependency) frames the bytes on the engine's own TLS stream, with ALPN `h2`. No relay (Firebase or another vendor) and no sidecar. One connection per delivery: opened, used for the user's devices, closed. (3) One environment per engine: `PONI_APNS_ENVIRONMENT` is `production` or `sandbox`, with one token-based key (`.p8`, environment-specific and topic-specific for the app's bundle id), its key id, the team id and the bundle id, all or none, from the environment only and checked in `load_config`. A registration for the other environment is a 400. The provider token (an ES256 JWT signed with OpenSSL) is kept 50 minutes and dropped on `ExpiredProviderToken`; the job's retry then sends again. (4) The outbound client takes one request to Apple: a `POST` to `/3/device/<token>` on the configured environment's host, the token hex only, refused by `http::why_refused` in any other shape. (5) A device belongs to the app session that registered it (`devices.session`, deleted with the session) and has no user, environment or last-seen of its own: a logout, an ended session and a disabled user stop its pushes. `POST /api/devices` stores the token for the calling session, one device per session, and a token another session had moves to this one; it writes an audit entry only when something changed. `DELETE /api/devices/{id}` removes the device. A device token is in no log. (6) A rule may have the channel `push` only for `escalation` and `system_problem`; its recipients are staff emails. A push rule is refused while no APNs key is configured. Push has no global switch: an enabled push rule is the person's switch (D-066's switch stays for email). (7) One delivery per user, as for email, which keeps the ids a push opens (`escalation_id`, `local_post_id`): the job sends to every device the user has at that moment. It succeeds when every device accepted or was dropped, any temporary failure retries the whole delivery, and the reason says how many devices were reached. A resend is harmless, because `apns-collapse-id`, from the event's key, replaces the alert already shown. (8) The alert is the event's `subject` under a fixed title per event type, never its body. The payload carries `event_type` and ids only (escalation, review, location, local post; `NotificationEvent` gains the escalation's and the post's id), a category (`ESCALATION` or `SYSTEM`), a thread id per kind (`escalation`, `system`, as the app asked) and a sound. (9) A device is dropped when APNs answers `410 Unregistered` or `400 BadDeviceToken`; a refused key, team or topic raises one `system_problem`. Supersedes D-020.
Why: Apple speaks only HTTP/2 and Beast only HTTP/1.1. nghttp2 is a small C library without dependencies that works on the stream the engine already owns, so the one thread, the TLS context and the write rules stay as they are, and only Apple sees an alert. At our volume (hundreds a day) every push service costs about nothing; what differs is work and parts: Firebase would change the app and add a Google host, a sidecar would add an image. Apple's advice to keep connections open does not matter at this volume, and pooling can come later. Tying a device to its session answers who may receive a push with the rules sessions already have. Push needs no switch of its own because it reaches only staff's own signed-in phones, while email can reach clients.

### D-104 · A report is one page in the bucket, sent any number of times, and discarded
The owner's decision of 2026-11-23; replaces D-085 points 4 and 10 and the draft, send-once and reject workflow. (1) A report is `building`, `failed`, `ready`, `discarding`, `discarded` or `expired`. There is no `draft`, `sent` or `rejected`: a report cannot be edited, so nothing waits for a decision before it is sent. (2) Records in the database, objects in the bucket. A report's page is not kept in the database (`reports.html` goes, and `GET /api/reports/{id}/html` with it); its numbers are (`reports.data`), because the API reads figures from them. The build renders the page, writes its object name to the row right before the upload and only while the report is `building` (`r/<32 random bytes>.<ext>`, point 11), uploads it, then marks the report `ready`, so that every object in the bucket is named by a row: a retried build keeps the name the row has, and a report that failed after its upload began still names it. The extension is the page's format, so that a later PDF or a page with images changes nothing else. (3) One link per report: its object's address, `Report.url`, while it is `ready`. No other share link, no route that makes or revokes one, no `report_share_links`. A link that reached someone it should not is withdrawn by discarding the report. (4) `POST /api/reports/{id}/send` may be called any number of times and changes nothing about the report. It goes to the recipients of the enabled `location_report` rules of the report's location (D-102 point 6), or to the subset of them the request names; an address that is not among them is a 400. It is refused unless the report is `ready`, the location is switched on, email sending is on with a sender connected (D-066) and there is a recipient. The request blocks until every address was tried. Each address gets its own message, one `To:` and no Bcc, through the Gmail channel, one after another. Afterwards one row per address is appended to `notification_deliveries` (`event_type` `location_report`, `report_id`, `requested_by`: the person, or null for a schedule), with its final `sent` or `failed` and Gmail's message, under a key of its own per send so that a second send is never dropped as a duplicate. The rows are not queued and not retried: a failure is a row, and a person sends again. `sent` means Gmail accepted the message, not that it arrived. The engine does not ask whether an address had the report before; `Report.deliveries` and `Report.recipients` let the client ask the person. (5) Auto-send: `reports.auto_send_status` is `off` (a person's report, or a schedule without "send automatically"), `pending` or `done`. The transaction that marks a build `ready` reads the send's checks: if they pass it sets `done` and the build sends, otherwise the report stays `pending` and a person can send it. `done` is written before the send, so that a schedule sends a report at most once; an engine that stops in between leaves `done` without rows, which is accepted. (6) `POST /api/reports/{id}/discard`, for a `ready` or `failed` report, refused while it is `building`: the row becomes `discarding` and names the archive, `a/<new 32 random bytes>.<ext>` in the same bucket, a name never cleared or replaced (point 14); the object is copied there, the original is deleted, and the row becomes `discarded`, its archive shown as `Report.archive_url`. Copy first, then delete. A report that never named a page (point 11) becomes `discarded` at once, without an archive. A call on a report that is `discarding` finishes it; a copy whose source is gone copies nothing and keeps the archive's name (point 14). A discard cannot be undone, and only a `ready` report is sent. The old link then shows Cloud Storage's own error page. The archive is the one copy the dashboard loads an old report from, and its address goes to nobody else. (7) The outbound client takes two more requests, both to the configured public bucket and nowhere else: the copy (`rewriteTo`) of an `r/` object to an `a/` object, and a DELETE of an `r/` object, each address equal to the one built from its parts. (8) The retention is our own, not Cloud Storage's: the bucket has no lifecycle rule. A clean-up script outside the engine (work-items) expires reports by the day they were built, by discard's steps with `expired` at the end, marks old draft and rejected local posts `expired`, deletes the uploads no open post or edit names, and deletes objects no row names once they are a day old. Until it exists nothing leaves the bucket. (9) The engine's limit for Gmail is 2 calls a second with a burst of 5, under Gmail's own of about 2.5 sends a second per user. (10) The copy is one call: inside one bucket, without a change of storage class, Cloud Storage finishes a rewrite in the one request, so an answer with `done` missing or `false` is a failure and its `rewriteToken` is not followed (it would put an opaque query on an address the client takes with no query, and a later call copies again, replacing the destination). The configured bucket reaches the outbound rule as a parameter given to the client at start (`http::NetClient`, `http::why_refused`), and with a folder or none the client sends neither request. POSTs to Cloud Storage are a closed list: an upload, to any bucket, and the copy. `storage::ObjectStore::copy` and `remove` take a report's names only (`storage::is_report_page`, `storage::is_report_archive`), in every store, and an error of theirs keeps Google's kind and status but not its words, which may quote the object's name. (11) Without a public bucket no report is started (the owner's decision of 2026-11-23): a person's "generate" is refused with 409 `no_public_bucket`, schedules start nothing, and a row that is `building` anyway fails with the reason. The page is named by the build in a transaction of its own right before its upload (`repo::name_report_page`), and nowhere else, which is also the check that the report is still `building`: a run that was overtaken (its job outlived the queue's lock, or the stalled-report sweep failed the report) uploads nothing, and a row names a page only if an upload of it was begun. Two runs inside that instant can still leave one run's page with the other's numbers. `0010_report_objects.sql` maps the old rows: `draft` and `sent` become `failed` ("Built before D-104; generate it again."; their page was in `reports.html` and goes with it, their numbers stay), `rejected` becomes `discarded` without an archive; `auto_send_status` is `pending` for a report that was `building` with auto-send, `done` for one its schedule sent, and `off` otherwise. It drops `report_share_links` although some links may still work: nothing is deployed, no real bucket was written to, and an object no row names is the clean-up script's to delete. (12) The production site's Content-Security-Policy (`deploy/Caddyfile`) allows a frame to `https://storage.googleapis.com/<public bucket>/` and to nothing else there (the owner's decision of 2026-11-23): the dashboard shows a report by framing its object's address, `Report.url` or `archive_url`, and the engine serves no page. The source ends in the bucket's name and a slash, so another bucket's object is blocked. It is the policy's last directive, so the name cannot replace a directive the policy has. Caddy reads the name from `PONI_PUBLIC_BUCKET`, as the engine does, and puts it in when it answers (`{env.PONI_PUBLIC_BUCKET}`), so it stays inside that header's value. The name is the operator's setting and nothing checks it: a value that is not a bucket's name (a space, a `;` with a directive the policy does not name) changes the policy, so the header is read after the name changes. (13) "No sender connected" is read from the stored mailbox, a credential with its address (D-100), and answers `sending_off` like the switch; whether its token still works shows as each address's failure. A schedule's mail is prepared in the transaction that marks the report `ready` (`repo::store_built_report`), so nothing is checked again between `done` and the send. Every address that was not accepted is `failed`, a thrown error included (with a reason that says the log has it, and the log line without the address), and every address is tried: a send is not cut short when Gmail limits the mailbox, so it may take minutes. (14) The `report.discard` audit entry is written when a discard begins, in the transaction that marks the report `discarding` (or `discarded`, for a report that never named a page), in the name of the person who began it (`repo::begin_discard`); the last step (`repo::finish_discard`) is the engine's bookkeeping and writes none, so a discard that breaks off still has its entry and a second person's call that finishes it adds none. The archive's name is written with `discarding`, before the copy, and is never cleared or replaced, also when the copy found no original: the engine cannot tell a page that was never stored from one an earlier call already moved (no column records an upload, and the engine reads nothing in the bucket), and clearing the name in the second case would leave the report's only copy to the clean-up script, which deletes an object no row names. So `archive_url` can, rarely, answer Cloud Storage's "not found" (a page named and never stored), and a report that never named a page has none. The original is deleted only after this call's copy succeeded or found no original. A discard believes a "not found" from the configured bucket (the page was moved by an earlier call, or never stored), since the engine reads nothing in the bucket and cannot check; it is only ever the bucket's answer, never a token that could not be had (`google::send` returns a token endpoint's 404 as `not_configured`). So the bucket's name must not change while pages of reports are in the old one: a discard would find no page in the new bucket, call the report discarded and leave the page readable in the old. A copy or a delete that fails, or throws, answers 502 `storage_failed` and leaves the report `discarding`, its `url` null although the old link may still work, and the next call starts again at the copy, which replaces the archive with the same bytes. A discard waits for nothing under way, and what that leaves is accepted as point 11 accepts the instant of the upload: the emails still to come of a send carry a dead link; a build of a report the stalled-report sweep failed, if it is inside its upload at the moment of the discard, can put a page back under its `r/` name, an object whose address nobody was given (the report was never `ready`) and which the row still names, so the clean-up does not delete it; and a second run of a build overtaken inside its upload (point 11) can do the same after the first run made the report `ready`, its schedule mailed it and a person discarded it, all within that one upload, and then the mailed link works again.
Why: what cannot change needs no approval, and one object per report gives one way to withdraw it. Pages belong in a bucket whatever their format, and the database keeps records. A send per address gives each address its own outcome; ten take a few seconds, which a loading indicator covers. Deleting at Cloud Storage is in our own bucket only, and copying first means a failed step loses no report.

### D-105 · In development the folder that stands in for the bucket is served by a local file server

(7) A post is deleted only because a signed-in person asked (`repo::request_local_post_removal`); a `NOT_FOUND` for a post the job could not read first proves nothing. (8) The sync reads posts hourly, marks one removed only after a get answered `NOT_FOUND`, and never writes. (9) Up to ten photos and videos (D-101), each checked from its bytes and stored exactly as uploaded as `p/<32 random bytes>.<ext>` in the public bucket, because Google fetches media only from a public address. (10) Checks in code (`domain::run_local_post_checks`): lengths, no contact details, an `https` button, a future time, a fetchable photo. (11) The model helps only when a person presses a button (`jobs::PostAdvisor`), stores nothing, never sees a reviewer's name or photo or a flagged review, and is not in the go-live fingerprint. (13) Not built: automatic posting, posts in the Google mock. Editing at Google was not built here either; it is D-099.
Why: deleting is the only way to stop a scheduled post or take down a wrong one, so the delete rule was lifted for local posts and for nothing else.

### D-090 · A local post can carry a video
MP4 or QuickTime, recognised from its bytes (`domain::inspect_video`), at most 30 seconds and 75 MB, 720 px on the short side; no codec check. The upload route alone has its own body limit (75 MB); for it the server checks the caller from the headers before reading the body (`Router::refuse_before_body`), and the file goes to disk, never into memory (D-101).

### D-094 · Copy a post, delete a draft, filter the list
(1) `POST /api/local-posts/{id}/copy` writes a new draft from any post and queues nothing; what a draft cannot hold is dropped and named, and a post made at Google brings no media (the engine fetches nothing from Google's media hosts). (2) `DELETE /api/local-posts/{id}` deletes only a `draft` or `rejected` post; never a `failed` one, because a send that was given up is still adopted when its post turns up at Google. (3) The list filters by `status` and `google_state` lists. (4) No one-step replace: it would make an approval cause a delete at Google. A correction of a post that is at Google is an edit in place instead (D-099), which deletes nothing.

### D-098 · The phone app's second round of requests
(1) `GET /api/local-posts` takes `order`, `asc` or `desc` (the default), over one key: the time Google created the post, or else the time the draft was written, then the id, both reversed by `asc`. There is no `sort` parameter: a parameter with one value is added when a second key exists. (2) The list's `google_state` filter also takes `none`: every post without a state from Google, whatever its `status` (a draft, a rejected draft, a post that is `approved`, `sending`, `unknown` or `failed`, and a sent post Google has not been read back for yet). It combines with the other values and with `status` as before. `none` is a word of the filter, not a state, so `LocalPostGoogleState` does not change. (3) A copy remembers the post it was copied from (`local_posts.copied_from_id`, set only by `repo::copy_local_post`), and keeps it whatever becomes of the copy; every post lists its copies with their status, newest first (`LocalPost.copies`). The link is lost when the post copied is deleted, and when it was a row the sync stored a moment before a send's own answer named the same post, which the send's bookkeeping removes (`local_post_send_accepted`). The link is not content: it is not approved or compared, travels in no request and changes nothing about sending, removing or the sync. It makes a correction findable from the post it corrects without editing anything at Google. (4) A `failed` post is still never deleted (D-094 point 2 stands): a send that was given up is still adopted when its post turns up at Google. The app collapses or ages out old ones on the device (the owner, 2026-11-21). (5) Editing a post at Google is not part of this entry: it is D-099, which the owner decided to build without the trial first planned. (6) `Location.time_zone` is the location's one time zone, which its posting window uses (D-110 point 2); a report takes the zone of the client's location with the lowest id that has one. `LocationUpdate` does not take it, and since D-110 removed `PATCH /api/locations/{id}/auto-posting`, where a person entered it, no route sets it. Date-times in the API stay UTC, `scheduled_time` and `recurrence.until` included; a posting window's and a report schedule's times of day are local. `Location.local_posts_sync_error_at` shows the time of the last failed read of the location's posts (the column was already there): a read that fails twice with the same message changes nothing else the app can see, and the app polls after "Refresh from Google". (7) `Report.average_rating` and `Report.response_rate` are read from the report's stored data, beside `new_reviews`, and are null while the report is building and where the period had no rated or no new reviews. Nothing is computed again: a report is built once and never changes (D-085). (8) An escalation's timeline is not a member of `Escalation`. It is two reads the app puts in order: the audit log of the escalation (`escalation.open`, `escalation.reopen`, `escalation.assign`, `escalation.close`, with who did it as `actor`) and the delivery log, which gained `NotificationDelivery.escalation_id` and the filter of the same name (the column came with D-097). The contract says where each is. There is no `assigned_by`: it is the `actor` of the assign entry. (9) The contract holds what a push says and what raises one: the schema `PushPayload` is the JSON given to Apple, and the description of `NotificationEventType` lists every `system_problem` event with its subject and the ids its push carries. A new `system_problem` event is added to that list when it is added to the code. There is one title for all system problems; the subject says what happened. (10) The app's sign-in answers the attempt limit with a redirect to `gbpmanager://auth?error=too_many_attempts`, at the start (`client=ios`) and at the callback (the attempt's cookie holds a note, as the app's start sets one), built by `login_error` like every other redirect to the app; the dashboard keeps the 429. Every request is still counted first, before its `client` or its cookie is read. Two failures stay: a callback that lost the attempt's cookie goes to the dashboard, because whose attempt it was is in that cookie alone and nothing of a redirect's target is taken from the request (D-095); a start's 400 for a missing or malformed challenge stays JSON, because only a fault in the app produces it. `POST /api/auth/app-token` keeps its 429: the app calls it itself.

### D-099 · A post at Google is edited in place
The owner's decision of 2026-11-21, on the app's request. It reverses D-088 point 3 ("nothing is edited at Google"), the "no PATCH" of D-042 and the three writes of D-061, for this one thing. **It was built from Google's documentation alone: a trial against Google was planned and then skipped by the owner, and no edit has ever been sent.** (1) An edit is its own row beside the post (`local_post_edits`, migration 0005), at most one open edit per post: the proposed content, the post's content it was written against (its base), the fields it changes, its checks, who wrote it and when, who approved it and when, the content that was approved, and a state (`draft` → `approved` → `sending`, and from each of the last two back to `draft` with a reason). The post keeps its row, its `id`, `google_name`, `status` (`sent`), `scheduled_time`, `sent_at`, author and approver, and its `content` stays what Google has: it changes only when Google accepted an edit or a read brings something else. `LocalPost.edit` shows the open edit or null, so that a second person sees it and an approver sees what they approve: its `content` is the post as it would say with the edit applied now (the post's content at that moment with the edit's fields laid over it, `domain::local_post_with_edit`), beside the fields it changes and the photo or video the post would show. A post can have an edit while it is `sent`, has a `google_name`, has no removal requested and belongs to a location linked to an active client; one made in Google's own interface too. (2) Three routes. `PUT /api/local-posts/{id}/edit` writes the edit or replaces it while it is a `draft`. Its body is two whole `LocalPostContent`: `content`, what the post should say, and `based_on`, the post's content as the person had it in front of them. `based_on` must be the post's content as the engine holds it now (409 `local_post_changed` otherwise, and nothing is stored); it becomes the edit's base. The content is normalized and checked as a draft, and every PUT rewrites the edit whole, also one with the same content: its writer, its time and its base. `DELETE` discards a draft edit, whose content the audit entry keeps. `POST …/edit/approve` carries the edit's content as the person read it and is refused unless it equals what the engine serves now after the same normalizing (so neither a replaced edit nor a post that changed in a field the edit leaves alone is approved unseen), has something to send, passes every check as things are now, both posting switches are on, the location is synced and the post still qualifies. An edit does not change the post's kind, its `scheduled_time` or its repeat: a 400 names the member, and for those a person still copies and removes. Two checks always pass for an edit because it does not send what they are about (`scheduled_in_future`, `recurrence_end`: a post that was scheduled and is live has a time in the past), and `media_usable` looks at an upload only when it is not the post's own. (3) **An edit never writes a field its author did not change.** The fields an edit changes are those, out of `summary`, `callToAction`, `event`, `offer`, `media` and `languageCode`, in which its content differs from its base (`domain::local_post_edit_mask`); the rest of what was sent is the post's own, there only because the content travels whole, and is neither shown as the edit's nor written. The base is what the person saw, never the post as the engine happens to hold it later: otherwise a field that changed at Google meanwhile would turn into a change of theirs. At the approval and again in the job, each of those fields is compared with what Google has now (`domain::local_post_edit_request`): Google has the edit's value, and the field is left out; Google's value is neither the edit's nor the base's, so that field was changed at Google since the edit was written, and the edit stops with a reason that names it (409 `local_post_changed`, or back to `draft` in the job) and nothing is sent; otherwise the field is in the mask. A field outside them is never named, whatever Google holds. After such a stop a person loads the post and saves the edit again, the served content against the post as it is now: the edit keeps exactly the fields they changed, on a base they have seen. `media` is among an edit's fields only when it names another upload than the post's or takes the post's upload away; a post whose photo is Google's own copy keeps it, and nothing is fetched from Google's media hosts. An event's repeat, and the days and times the edit does not change, go back as Google holds them. A post that holds what a draft cannot hold (an alert, a button outside the six, an event or offer without its dates) is not edited here at all (409 `local_post_not_editable`): an edit is content a draft can hold, so it could not say how to keep that part. An edit with nothing to send cannot be approved. (4) The write is one address: `PATCH https://mybusiness.googleapis.com/v4/accounts/{a}/locations/{l}/localPosts/{p}?updateMask=<names>`, plain ids, the query exactly `updateMask=` and one or more of the six names, each once, joined by commas, equal character for character to the address built from its parts (`http::is_local_post_update_url` in `http::why_refused`). Every other PATCH, anywhere, is refused. It is the one exception to "a write's address has no query". `gbp::LocalPostWriter` gained the update, called only by the job. Against the Google mock nothing about edits is started. (5) One PATCH per approval. `repo::approve_local_post_edit` is the only function that enqueues `local_posts.edit`. The claim checks, in one transaction, the approval (not older than 30 minutes, and what the post would say with the edit applied is what was approved), both switches, the location, the checks and that the post still qualifies, and marks the edit `sending`; an edit it stops returns to `draft` with the reason and is never sent later by itself. The job reads the post under the location's own ids as they are now (a post whose stored name belongs to another location is not touched), stores that read as the sync would, and works out the mask against it as point 3 says. If the post changed at Google since the approval so that it would no longer say what was approved, also in a field the edit leaves alone, nothing is sent and the edit returns to `draft` to be approved again. `NOT_FOUND`: the edit returns to `draft`, and the job marks nothing removed. A read that fails because Google is busy or cannot be reached (a 429, a token error, a 5xx, a timeout) is tried again while attempts are left, because nothing was sent; any other answer to the read returns the edit to `draft` at once. Nothing to write: Google has what the edit changes, and the edit is done without a request. Then the PATCH, once. Accepted: the post's row takes Google's answer, `edited_by` and `edited_at` name the edit's author and the moment, the edit's row goes, and the audit entry keeps the content before and after and who approved; where the answer does not say what was sent, staff are notified and the edit is settled all the same. A certain refusal (the same list and function as for a create: 400, 401, 403, 404, 429, or no token): a rate limit or a token error returns the edit to `approved` for the job's next attempt, anything else returns it to `draft` with Google's message; the post is untouched and staff are notified. Anything else (a timeout, a dropped connection, a 5xx, a 408, 409 or 499, a 2xx that cannot be read or names another post): the PATCH is not sent again, the edit returns to `draft` saying that Google did not confirm it and that "Refresh from Google" shows what the post says now, staff are notified, and the row is not changed by guesswork; a person may approve again. After an edit that Google accepted or did not confirm, the location's posts are read again 1, 5 and 15 minutes on, as after a send. There is no `unknown` state for an edit, and the sync never settles one. An edit that is `sending` is never sent again and never given back by its age: a job that finds it so leaves it, and only once no job for it is queued or running does `local_posts.sync_due` give it back as not confirmed (where an approved edit whose job is gone returns to `draft` too). So after the engine stopped between the claim and the bookkeeping, an edit shows as being sent until its job's lock has expired and the job has run, 40 minutes by default. A claim is named by its moment (`send_started_at`): the job carries it, and every later step, the one before the request included, acts only on the edit as claimed at that moment and no later than 30 minutes after it, so a run that outlived its lock neither sends nor settles an edit that was given back and claimed again. (6) Removal wins: `repo::request_local_post_removal` is never blocked by an edit, discards a draft edit with the request (its content in the same audit entry), and an approved edit is stopped where its job claims it and again where its PATCH would start; a PATCH already on its way is not called back, and its bookkeeping and the delete do not wait for each other. A post that is removed, or whose location is unlinked, keeps no approvable edit: only a discard. The sync overwrites a `sent` post's content as before, edit open or not, and never touches an edit. Copy, delete, reject and the publish path are unchanged; a copy takes the post's content, not its open edit. The posting switches apply; there is no switch of its own. Three `system_problem` events: `A post could not be edited`, `An edit of a post may or may not have reached Google` and `Google accepted an edit, but the post does not show it`, each with `location_id` and `local_post_id`; and `Google rejected a post` is now told each time it happens, because an edit can get a post rejected again. (7) What the first real edits will show, because nobody could find out without sending one: which of the six fields Google takes in `updateMask` (its guide shows `summary` only); whether an edit sends a live post back to `PROCESSING`, or can get it `REJECTED`; and whether a post that is scheduled and not yet published can be edited at all. The design needs none of these answers in advance: a field Google will not take comes back as a refusal with Google's message, a field it takes and ignores is noticed in its answer, and whatever state Google gives the post is read back as for any post. What the code takes from the documentation without proof: that a 400, 403 or 404 to the PATCH means nothing was changed; that a field named in the mask replaces that field whole, and one named and left out of the body is cleared; that the PATCH answers with the post as it then is, under the same name; that a field outside the mask is left alone; and that a read of one post says what the list of the location's posts says about it, since an approval made from the one is checked against the other.
Why: a correction must stay the same post. With copy-and-remove the corrected post is a new one that says nothing of when the original was scheduled, approved and by whom; both are live until someone removes the old one; and every correction leaves a draft and a removed post behind (the app's request 1). The approval rule stays whole because an edit is approved like a first send: the exact content, by a signed-in person, checked again at the claim. The content travels whole, so an edit carries fields its author never touched; writing those back would undo what a client changed in Google's own interface meanwhile, which nobody approved. Hence the base: what a person changed is what they are answerable for, and a change on both sides is theirs to look at, not the engine's to settle. The base comes from the client because only the client knows what the person was looking at; the engine checks it against the post, and shows and compares the edit laid over the post as it is, so that neither a form loaded before a read nor a second save can make a stale field the edit's own. One PATCH per approval with no resend, because the outcome of a write that got no answer is not known and the engine never repeats such a write by itself; unlike a create, though, an edit that may have arrived cannot leave a second post behind, and the next read shows the truth, so nothing has to settle it: the person is told, looks, and approves again if needed, which is harmless because the same content sent twice changes nothing. An edit that is `sending` is not given back while its job may still send, because a person could approve again and the first request, arriving late, would undo the second; waiting for the job's lock costs minutes of an edit shown as being sent, after a crash only. The kind and the time are left out by the owner's decision: a post's kind decides which parts it has, and Google's v4 reference shows no scheduling field on a post at all, so nothing says an edit could move a time.

### D-101 · Up to ten photos and videos per post, uploaded to disk
The owner's decision of 2026-11-22. (1) A post's content names its uploads as `media_ids`, a list in the order the post shows them, at most ten, photos and videos mixed, each at most once; more, or one twice, is a 400 (`domain::normalize_local_post`). It replaces `media_id` (one upload or null); the phone app had not shipped, so the member was renamed in one go. Migration 0007 rewrote every stored content (a post's content and approved content, an edit's content, base and approved content) and dropped the generated `media_id` columns and their foreign keys: PostgreSQL has no foreign key on the elements of a list, the engine checks on every save that each id names an upload, and nothing deletes an upload. (2) Ten is what Google's own interface takes, as reported by Search Engine Roundtable and the Local Search Forum (February 2020) and Whitespark's guide (February 2026), with media shown as a carousel. Google's API documents no number and no example with more than one item. Google's own answers do hold several: the sanitized list in `tests/fixtures/local-posts-list.json` has a post with three photos and one with a video. That the API accepts several on a create, mixed, and keeps their order is taken without proof until the first trial (work-items, "The first real local posts"); a number Google refuses comes back as a refusal with Google's message, as any 400. (3) The create and an edit send `media[]` in the list's order. In an edit `media` stays one of the six fields: Google replaces it whole, so any other list, a new order included, is a change of the media and sends every file again, and `media_usable` then looks at every upload of the list. A list of uploads replaces everything a post shows at Google, Google's own copies of files included. A copy keeps every upload and leaves out Google's copies, naming how many. The sync keeps the uploads it has stored for a post, as before. (4) One file per request: `POST /api/local-post-media` is unchanged, a client uploads each file, in parallel if it likes, and lists the ids. For a route that takes a file (`RouteInfo::max_body_bytes`) the server streams the body into a file in the system's temporary folder that is unlinked the moment it is opened (`core::nameless_file`), and the route reads it through a read-only mapping (`core::MappedFile`, `Request::file`); the bucket upload sends it from the mapping as the body of a plain media upload (`uploadType=media`, `ClientRequest::file`, only in a POST and never over HTTP/2), without metadata of its own, so Cloud Storage serves it with its default for a public object, an hour in caches, as before. So memory does not grow with the size or number of uploads, no limit on uploads at once is needed, and nothing is left on disk after a request or a crash. (5) The engine cleans up no upload. The clean-up script (D-104 point 8) deletes an upload that no open post or edit names; until it exists an upload stays in the bucket, under a name nobody can guess and in a bucket that cannot be listed.

## Sign-in and sessions

### D-007 · Internal users, one role, full audit log
Every route passes the one authorization hook, so roles can be added later.

### D-033 · Sign-in is Google sign-in
Workspace accounts of the listed domains only (D-053); no passwords; server-side sessions; the audit log records the Workspace email. A user row is created at first sign-in or, before it, from the Workspace directory by a signed-in person (D-106 point 8).

### D-040 · The dashboard's session
A random token in an `HttpOnly`, `SameSite=Strict` cookie (`__Host-` and `Secure` over HTTPS), its hash in the database; 7 days at most, 24 hours idle. A changing request needs `X-CSRF-Token` and, when sent, our own `Origin`.

### D-041 · Development sign-in
`POST /api/auth/dev-login` works only with `PONI_DEV_LOGIN_EMAIL` set and `PONI_PUBLIC_URL` plain `http://localhost`, so one stray variable cannot enable it in production. It is how CI's contract check and the Google mock sign in.

### D-043 · The stored GBP credential
Client ID, client secret and refresh token together (a refresh token works only with its client), encrypted with AES-256-GCM (`core::SecretBox`) under `PONI_SECRET_KEY`; stored only from the dashboard (D-079 point 2).

### D-053 · Sign-in domains
`PONI_SIGNIN_DOMAINS` (`xvisionmediaus.com`, `xvisionus.com`). An account gets in when its address is verified and both its Workspace organization (`hd`) and its address's domain are listed (`http::domain_allowed`).

### D-095 · Sign-in for the phone app; two kinds of session
(1) One Google sign-in for both, every check in the dashboard's code path: the app starts with `client=ios` and a PKCE S256 challenge, and its callback redirects to the constant `gbpmanager://auth` with a one-time code, setting no cookie. (2) `POST /api/auth/app-token` exchanges code and verifier for a bearer token; a code lives 60 seconds, is stored hashed and is spent by the first request (`repo::take_app_code`); every refusal is the same 400. (3) A session is `browser` (cookie) or `app` (`Authorization: Bearer`, that header only), both through `AuthService::authorize`; a bearer request gets no CSRF or Origin check. (4) An app session lasts 30 days idle, 90 at most. (5) An inactive user has no session; the staff check deletes a person's sessions when it disables them (D-106 point 6). (6) Logout with a token ends it. (8) From the app's first release, removing or renaming a response member or narrowing a response enum is breaking and agreed first; adding is not. No token, code or verifier is logged or put in an address.
Why: the browser sheet cannot hand a cookie to the app, and PKCE (RFC 8252) makes a code caught by another app useless.

### D-100 · A connection is the Google account that signed in
(1) The three Google connections, the GBP managing account, the sending mailbox and the Workspace administrator (D-106 point 2), are the account a signed-in person signs in with after pressing **Connect** on the status page (D-079 point 2). No setting names any account or its address: `PONI_EMAIL_FROM` is removed (`PONI_EMAIL_FROM_NAME`, the name shown beside the address, stays). (2) Each connection asks Google for `openid email` beside its own scope and always shows Google's account chooser (`prompt=select_account consent`). The engine takes the account's address from the verified `email` claim of the ID token of its own code exchange (D-091 point 12) and stores it beside the credential (`credentials.account_email`), replaced with the token on every connection; an answer without a verified address is refused (`no_email`) and stores nothing. (3) The status serves the address of each connection (`GbpStatus.account_email`, `EmailStatus.account_email`, `WorkspaceStatus.account_email`), so a client can be told which account to invite, and email is sent from the mailbox's stored address. A credential stored before this has no address: the status shows `null` until the account is connected again, and no email is sent until the mailbox is. (4) One connection of each kind at a time: connecting another account replaces the token. A GBP account that manages other locations shows the old ones as lost through the usual discovery (two listings) and nothing else.
Why: the account is chosen where it is proved, by the person who signs in with it, so moving to another account (D-009) is a click and not a change of the configuration, and nothing the status says about an account can disagree with the token that is stored.

### D-106 · Who may use the engine is decided in the Workspace directory
(1) **One switch.** A person may use the engine while their Google Workspace account is active, and the engine follows the directory by itself. Nobody disables or enables a user in the engine by hand: there is no route and no dashboard action for it. To shut someone out, suspend or delete their account at Google; the engine follows at its next check, within five minutes. (2) **A third connection, `workspace`,** beside the GBP managing account and the sending mailbox (D-079 point 2, D-100): the account a signed-in person signs in with on the status page, an administrator of the Workspace. Its refresh token is stored encrypted (D-043) with its address. It asks Google for `https://www.googleapis.com/auth/admin.directory.user.readonly` (and `openid email`, D-100) and for no scope that can write. It is stored only if that scope was granted, the account's address is of the sign-in domains (D-053), and the directory's list of users, read with the new token, holds the account under the `sub` of its own ID token, with the same address, neither suspended nor archived, as an administrator: that shows the enabled API, and on every connection that a Directory user's id is the `sub` a sign-in carries. The account should hold a custom admin role with "Users: Read" and nothing more, given for the whole organization; a super admin is accepted, because the token can only read, but is not what should be connected. (3) **One request, a read.** At `admin.googleapis.com` the outbound client takes one request, a GET of the list of the account's users (`customer=my_customer`, 500 a page, and Google's page token), and nothing else (`http::why_refused`). The engine never suspends, creates, edits or deletes anything in a Workspace, and never asks about one user, by id or by address. (4) **The staff check.** Every five minutes (`PONI_STAFF_CHECK_INTERVAL_S`) a job reads that list, every page, and is the only thing that changes a user's status: it disables an active user who is gone by point 5, and enables a disabled user whom the list holds with an account that is neither suspended nor archived. Only users whose `google_sub` is a Google id are judged; a row from development sign-in never is. (5) **What counts as gone.** A run judges nobody unless it read every page without an error and the list holds the connected administrator's address, neither suspended nor archived, as an administrator. Then every user the list does not show as active is gone: the list holds their id as `suspended` or `archived`, or does not hold their id at all, whatever their domain and however new their user. The engine trusts the list: there is no limit on how many one run disables. A run that could not read the list, or whose list does not hold the administrator, changes nothing, says so on the status page, and staff are told once a day. (6) **What a disable does.** In one transaction: the status becomes `disabled`; the person's sessions (and with them their devices) and their unspent one-time codes are deleted; an audit entry as `system:workspace` says what Google said; and a `system_problem` names the person. The user's row stays: everything they did still names them, and the API shows them as disabled (`User.status`, `GET /api/users?status=disabled` or `all`), so their colleagues see them as inactive wherever they appear. What the person approved before still goes out, and email to their address still goes until it is taken out of the notification rules; the notification says so. An enable is audited and notified the same way and creates no session: the person signs in again, which asks Google once more. (7) The same run refreshes a user's name from the directory. Photos stay what the last sign-in said: Google documents the directory's photo address as possibly private. (8) **People who have not signed in.** A signed-in person can pick someone from the directory (`GET /api/users/directory?q=`) and make them a user (`POST /api/users` with the Directory id) so that they can be assigned an escalation before their first sign-in. The engine finds the person in the directory's list itself and takes nothing about them from the request; only addresses of the sign-in domains are created, and never a suspended or archived account; the row is keyed by the Directory id as `google_sub`, has no session and no sign-in time until its person signs in, and that sign-in finds it. (9) **The mock** (D-087) serves the Directory list the engine reads, on made-up staff, with portal actions that add, suspend, delete, restore and rename one. (10) **Not decided here:** roles from Google Groups and staff tied to locations are later decisions, each with scopes of its own; a new scope means a person connects the account again. **Not built:** disabling or enabling by hand (point 1); a "check now"; comparing the sign-in domains with the Workspace's own (it needs a further scope and a wider admin role than point 2 allows); a flag on notification rules whose recipient was disabled (a rule's recipients are addresses, not users).
Why: a person who left kept a dashboard session for up to 7 days and an app session for up to 90, because the engine asked Google about a person only at sign-in. The directory is where a person's account is closed anyway, so it is the one place that decides; a second switch in the engine would be a second thing to remember and a second thing to get wrong. One list per run is one request at this team's size. The engine trusts what the list says about each person, once the list was read whole and holds the administrator who read it; that last check keeps an empty list, or another account's, from disabling everyone at once.
